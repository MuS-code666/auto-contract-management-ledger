# 設計メモ

## 1. 構成

```
app/
  main.py         FastAPI（127.0.0.1）・API・セキュリティ（Host検査、更新系の独自ヘッダー必須、CSP）
  config.py       パス・既定設定・初期カテゴリー
  db.py           SQLite 接続、スキーマ移行（PRAGMA user_version）、設定の読み書き
  repo.py         台帳の登録・更新・検索・履歴・関連・重複候補・期限一覧
  storage.py      PDFの保存・移動、安全なファイル名、管理ルート外防止、ジャーナルと復旧
  admin.py        カテゴリー（名称変更時のフォルダ移動）・保存ルート（新規のみ／移行）
  jobs.py         取込み・解析ワーカー（1件ずつ、キャンセル、タイムアウト、再解析、中断復旧）
  pdftext.py      PDF検査・ページ文字取得・利用可能性判定・ページ画像化・空ページ判定
  ocr/            OCRアダプター（RapidOCR / Tesseract / 無効）
  llm/            LLMアダプター（OpenAI互換ローカルサーバー / 無効）、ループバック限定
  extract/
    common.py     文書モデル（ページ連結・位置→ページ）、項目結果の形式
    rules.py      ルール抽出（モデル不要）
    llm_extract.py LLMプロンプト・JSONスキーマ・検証・チャンク統合・ルールとの統合
  dates.py        和暦/西暦/漢数字の日付解析、期間計算（月末・うるう年）
  deadlines.py    通知期限候補・次回満了日候補・期限分類
  excel.py        .xlsx 出力
  backup.py       バックアップ・復元
  static/         画面（HTML/CSS/JS、外部依存なし）
```

## 2. データ構造（SQLite）

| テーブル | 内容 |
|---|---|
| contracts | 台帳。内部ID(UUID)、管理番号(UNIQUE)、確定値、原文、構造化通知条件(JSON)、通知期限の候補・計算方法・確定値、管理上の期限、PDF（保存ルートID＋相対パス）、元ファイル名・ハッシュ、確認状態、`field_meta`(JSON)、各日時、論理削除日時 |
| parties / signers | 当事者（当社/相手方/その他、甲乙等の表示）と署名者（所属当事者への参照）を別テーブルで保持 |
| relations | 関連契約（種類・方向・メモ）。元の契約の値は変更しない |
| history | 修正履歴（操作・項目ごとの旧値/新値） |
| imports / import_pages | 取込み（状態・段階・抽出結果JSON・下書きフォーム・利用者が編集した項目）と、ページごとの文字情報（既存テキスト/OCR、状態、本文） |
| file_ops | ファイル操作ジャーナル（登録・移動の処理状態） |
| categories / storage_roots / settings / counters | カテゴリー、保存ルート、設定、採番カウンター |

`field_meta` には項目ごとに、抽出値・根拠ページ・根拠原文・由来（text/ocr）・抽出方法（rule/llm）・状態（未確認/修正済み/記載なし/要確認/読取不能/手入力）・別候補を保持する。抽出値と確定値は別に残る。

## 3. 抽出の流れ

1. ページごとに PDFium で文字を取得し、文字数・文字化け率で「利用可能」か判定。
2. 利用できないページだけ画像化（1ページずつ・処理後に削除）→ 空ページ判定 → OCR。
3. ルール抽出（常に実行）。見つからない項目は、未処理ページがあれば「要確認」、無ければ「記載なし」。
4. LLMが有効なら、ページ単位のチャンク（約6,000文字）ごとに JSON スキーマ付きで問い合わせ、pydantic で検証、根拠原文の実在確認、日付は原文から本アプリが正規化。チャンクの失敗は記録し、解析完了とはしない。
5. ルールとLLMを統合。値が食い違えば「要確認」とし両方の候補を残す。
6. 利用者が編集した項目（`user_edited`）は再解析で上書きしない。

## 4. ファイル操作の整合性

SQLite 更新とファイル操作は原子的にできないため、`file_ops` に状態を記録する。

- 登録: `pending` → `.part` にコピー → ハッシュ検証 → 上書きしない改名 → `file_done` → 契約INSERTと `completed` を同一トランザクション。失敗時・起動時復旧では未参照の保存先ファイルを削除し `rolled_back`（取込み一時ファイルは残るので再登録可能）。
- 移動: `pending` → コピー・検証 → `file_done` → DB更新と `db_done` を同一トランザクション → 移動元削除 → `completed`。`db_done` で止まった場合は起動時に移動元を削除。
- 管理番号は採番時点でコミットし、登録失敗でも再利用しない。
- すべてのパスは保存ルート配下であることを検証する（`safe_join`）。ファイル名は禁止文字・予約名・末尾ドット・長さを処理し、パス全体が240文字を超える場合は管理番号を残して短縮する。

## 5. バックアップ

SQLite バックアップAPIでスナップショット → `storage_lock` を保持したままPDF・下書きをZIP化 → manifest（ハッシュ）→ 検証。復元は、検証 → 復元前自動バックアップ → ステージングで展開・整合性検査・スキーマ移行 → PDF書戻し（異なる同名ファイルは改名して残す）→ バックアップAPIで台帳DBを置換 → PDF参照を検証。

## 6. スキーマ移行

`db.MIGRATIONS` に関数を追加し、`PRAGMA user_version` で版を管理する。移行前に `data\backups\pre_migrate_v<版>_<日時>.db` を作成する。アプリより新しい版のDBでは起動しない。

## 7. 期間計算のルール

- 応当日：同じ日。存在しない場合はその月の末日（1/31 の1か月後 → 2/28 または 2/29）。
- 期間の末日（開始日を含む n か月）：応当日の前日。応当日が無い場合はその月の末日（2024/4/1 から1年 → 2025/3/31、2024/2/29 から1年 → 2025/2/28）。
- 「○日前」は暦日で減算。営業日・休日は考慮しない。
- 計算値は「候補」として表示し、確定は利用者が行う。
